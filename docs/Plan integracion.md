## Plan: Integración de Análisis de Rentabilidad SabioGo

Con base en la investigación exhaustiva, he identificado que aunque las tablas staging `stg_sabiogo_ventas` y `stg_sabiogo_compras` existen en PostgreSQL con datos cargados (7,342 y 493 filas respectivamente), **no tienen modelos Python** y faltan completamente las capas de mapeo y análisis para habilitar rentabilidad real por producto. El sistema actual solo calcula márgenes como diferencia de precios (efectivo vs contrato) sin vincular costos reales de compras.

El plan implementa una arquitectura de capas (staging → mapeo → facts → análisis) siguiendo los patrones existentes del proyecto (Repository-Service-Controller, DTOs, BaseCRUD) y se integra con el módulo bi.py existente que ya maneja dashboards y KPIs.

**Decisiones clave:**
- **Método de costeo:** Promedio ponderado por producto/período (más simple que FIFO/LIFO para primera iteración)
- **Arquitectura:** Vistas materializadas para facts (mejor performance en consultas analíticas vs tablas regulares)
- **Carga de datos:** Inicio manual con UI administrativa, base para automatización futura
- **Mapeos:** Tablas de traducción dedicadas con UI de mantenimiento (no matching automático inicial para evitar errores)

```
CREATE MATERIALIZED VIEW fact_ventas_sabiogo AS
SELECT 
  v.fecha, v.codigo, pm.product_id, cm.client_id, lm.location_id,
  v.vendedor, v.forma_pago, v.tipo,
  SUM(v.kilos) as kilos_total, SUM(v.cajas) as cajas_total,
  SUM(v.neto) as ingresos_neto, SUM(v.subtot) as ingresos_bruto
FROM stg_sabiogo_ventas v
LEFT JOIN sabiogo_product_map pm ON v.codigo = pm.codigo AND pm.activo
LEFT JOIN sabiogo_client_map cm ON v.cliente = cm.cliente AND v.condicion_iva = cm.condicion_iva
LEFT JOIN sabiogo_location_map lm ON v.sucursal = lm.sucursal
WHERE v.estado = 'procesado'
GROUP BY v.fecha, v.codigo, pm.product_id, cm.client_id, lm.location_id, v.vendedor, v.forma_pago, v.tipo
WITH DATA;

CREATE UNIQUE INDEX idx_fact_ventas_pk ON fact_ventas_sabiogo (fecha, codigo, vendedor, forma_pago);
CREATE INDEX idx_fact_ventas_product ON fact_ventas_sabiogo (product_id, fecha);
```

Similar para `fact_costos_sabiogo` desde `stg_sabiogo_compras`. Crear vista `vw_margen_producto` que une ambos facts calculando margen por producto/período.

### **Decisiones**

**1. Método de costeo: Promedio ponderado**
- Elegido sobre FIFO/LIFO por simplicidad de cálculo en vistas SQL y suficiencia para análisis inicial de margen. FIFO requiere tracking de lotes que no está en staging actual.

**2. Vistas materializadas vs tablas regulares para facts**
- Materializadas permiten refresh on-demand sin duplicar datos, mejoran performance de lectura en BI (queries complejas pre-computadas), y mantienen trazabilidad a staging como fuente única.

**3. Carga manual inicial de XLS**
- Automatización (cron) depende de estabilidad de formato XLS y validación de reglas de negocio. UI manual permite supervisión y ajuste de mapeos antes de confiar en proceso desatendido.

**4. No matching automático de clientes/productos**
- Alto riesgo de falsos positivos por variaciones de nombre/ortografía en datos de SabioGo. Tabla de mapeo con UI administrativa da control y permite auditoría de decisiones de equivalencia.

**5. Integración en BI existente vs módulo separado**
- Reutiliza infraestructura de bi.py (ya tiene autenticación, templates, KPIs) pero servicio dedicado `SabiogoService` mantiene separación de concerns y facilita testing aislado.
